# Codex second-opinion review — lore codebase (2026-07-20)

## Summary

A full-codebase second-opinion review using OpenAI Codex (`gpt-5.6-sol`, primarily `ultra`
reasoning effort with `xhigh`/`high` fallback on timeout), run as 25 module-scoped clusters
covering all of `src/` (55 files, ~19k LOC), `bin/lore.cjs`, the Docker e2e harness, CI
workflows, and build/package config. Every file's cluster instructed Codex to also read and
assess its corresponding `test/*.test.ts` file for coverage gaps.

Every Codex finding was independently adjudicated by a second pass that opened the *real,
current* file at the cited location and confirmed or dismissed it — Codex reads a repo
snapshot and can hallucinate details, cite stale lines, or flag an intentional, documented
design choice as a bug. Nothing below reached this document without that verification step.

**Coverage: 25/25 clusters, 100% of scope.**

|---|---|
| Confirmed findings | 201 |
| — High severity | 20 |
| — Medium severity | 84 |
| — Low severity | 97 |
| Dismissed (Codex raised, adjudication ruled not real / not actionable) | 76 |

## Methodology notes (for context on how to read this)

- **Multi-round review.** `ultra`-effort Codex passes proved unreliable on multi-file clusters
  (systematic ~570s internal timeouts on the first pass), so failing clusters were re-split
  into 1–3-file passes and re-run with escalating effort fallback. Partway through, the
  connected Codex/ChatGPT account hit a hard usage-limit wall (confirmed directly — even a
  trivial call failed) that blocked 10 clusters entirely until a plan upgrade cleared it.
  Net effect: some clusters (`core-bundle-check`, `cli-entry-state`) were independently
  reviewed twice by Codex; overlapping findings were deduplicated, and the small number of
  genuine disagreements between passes were resolved during adjudication.
- **Severity** is judged by real-world blast radius (does it corrupt user data, crash
  silently, cross a security boundary, or is it a minor rough edge), not by how the finding
  reads in isolation.
- **Dismissed findings are kept** (condensed, in the appendix) as an audit trail — several
  are Codex correctly-flagged-but-actually-intentional design choices (e.g. ADR-0012's
  documented no-locking policy on Backlog commits), which is useful evidence the adjudication
  pass was actually skeptical rather than rubber-stamping.

## Headline risks

A few findings recur across independent review passes at different layers of the same call
chain, which is a stronger signal than any single finding alone:

- **`lore rename`'s destination id is never confined to the bundle root, at every layer that
  could have caught it.** `commands/args.ts:68` (id-parsing validates reserved stems only),
  `commands/rename.ts:122` (destination path never checked against `docs/`), and
  `core/rewrite.ts:164` (the shared rewrite engine has no containment check either, unlike
  its sibling `lore new --out`) — three separate clusters, three separate files, same gap.
  `lore rename docs/x ../../outside` can move/overwrite a file anywhere on disk.
- **Custom `.lore/profile.toml` templates allow path traversal into an arbitrary file read.**
  `core/profile.ts:400` (template name parsed with no traversal check) feeding
  `commands/new.ts:344` (joins it under `.lore/templates/` and reads whatever that resolves
  to) — a malicious/compromised profile can make `lore new` embed any readable file's
  contents into a generated concept.
- **A crafted concept file can crash or hang most `lore` commands.** `core/concept.ts:262` —
  `yaml.load` has no anchor/alias expansion limit; a small (~400 byte) YAML-anchor payload in
  frontmatter expands to 64MB+ on re-serialize (measured), an unhandled `RangeError` that
  `serializeConcept`'s many callers (bundle, sync, rewrite, indexes, template, scaffold,
  link, supersede) don't guard against.
- **`loadBundle` never uses a project's own custom profile** (`core/bundle.ts:158`) — every
  graph-backed command (query, context, graph, orphans, rename, tasks, sync, link, supersede)
  silently validates against the *built-in default* profile instead, so any project with
  custom types/fields either gets spurious validation errors or missed real ones.
- **Silent data loss in the managed-block engine**, twice: `core/indexes.ts:285` collapses
  and deletes hand-authored prose sitting between duplicate/malformed markers instead of
  failing loudly, and `core/replace.ts:84`/`commands/replace.ts:125` — the managed-region
  registry was never updated for the `lore:tasks` marker added by LORE-22, so `lore replace`
  can silently corrupt a Story's live task table.
- **`lore schema --out` can irreversibly delete files outside its own directory**
  (`commands/schema.ts:156`) — a full export's orphan-pruning step `rmSync`s every
  `*.schema.json` under the resolved `--out` path that the current profile doesn't emit, with
  no check that the directory is lore-owned; `--out .` deletes unrelated files.
- **`process.exit()` right after `run()` can truncate large piped JSON output**
  (`cli.ts:373`) — reproduced directly (65,536-byte truncation on a >64KB write), silently
  corrupting `--json` output for `query`/`graph`/`context` piped into another process, with
  exit code 0.

## High-severity findings (full detail)

#### `src/cli.ts:373` — process.exit(code) immediately after run() resolves can truncate stdout when output exceeds the pipe buffer, corrupting piped JSON.

*Category: correctness · Cluster: `cli-entry-state`*

Running `lore query ... --json | somewhere` (or graph/context) on a bundle whose JSON envelope exceeds ~64KB: Bun's process.stdout.write to a pipe is asynchronous, and process.exit() tears down the process before the write drains. Reproduced directly against this repo's Bun runtime: `bun -e 'process.stdout.write("x".repeat(200000)); process.exit(0)' | wc -c` yields exactly 65536, silently dropping the remaining ~134KB. Any consumer piping large lore output (CI capturing JSON, agents streaming query/graph/context results) gets truncated, invalid JSON with exit code 0.

#### `src/state.ts:193` — The backlog/ scope guard in commitBacklogFiles uses a plain startsWith("backlog/") check, which a literal-pathspec ".." segment defeats, letting a path like "backlog/../docs/secret.md" pass the guard yet resolve (and get staged/committed) outside backlog/.

*Category: security · Cluster: `cli-entry-state`*

Verified empirically against real git: git add -- ':(literal)backlog/../docs/secret.md' and git commit -m x -- ':(literal)backlog/../docs/secret.md' both resolve and commit docs/secret.md even though the pathspec text starts with 'backlog/' and passes the guard's startsWith check. If a Backlog task path ever contains '..' (a corrupted/drifted filePathRelative, or a future Backlog layout bug), lore would silently commit a file outside backlog/, violating the ADR-0012 sole-committer invariant and potentially sweeping an unrelated dirty file into a lore-authored commit. The guard's own doc comment even claims to defend against 'an absolute/`../` path', which it demonstrably does not.

#### `src/commands/check.ts:732` — `--external` performs unrestricted fetch() GETs to any http(s) URL found in bundle markdown, with no protection against loopback/private/link-local/cloud-metadata targets or malicious redirects.

*Category: security · Cluster: `cmd-check`*

A CI job runs `lore check --external` against an untrusted fork PR (or any PR from an external contributor); the PR's markdown contains a link to `http://169.254.169.254/latest/meta-data/` or an internal-only service URL, and probeOne's plain `fetchFn(url, {signal})` (line 732) issues the GET with no IP-range allowlist, no `redirect: "manual"` re-validation, and no HEAD-preference — enabling SSRF against the CI runner's network from doc content alone.

#### `src/commands/new.ts:344` — `--template <name>` is interpolated into a file path with no basename/traversal validation, letting a caller read arbitrary files elsewhere on disk (ending in .md) and copy their contents verbatim into a new bundle concept.

*Category: security · Cluster: `cmd-crud-a`*

Repro confirmed: `lore new adr "Test" --template ../../../../../../tmp/outside_secret --out docs/adr/test.md` reads /tmp/outside_secret.md (outside .lore/templates/ and outside the repo) and writes its exact bytes into the new concept body under docs/. No realpath/basename check confines the resolved template path to .lore/templates/.

#### `src/commands/orphans.ts:135` — The orphans report has no cap/truncation despite docs/reference/cli-contract.md §3 explicitly naming `orphans` as one of the read-heavy commands subject to the bounded-output-with-truncation-hint contract; a regression test (LORE-51) enshrines rendering all 700,000 rows unbounded.

*Category: api-design · Cluster: `cmd-crud-a`*

cli-contract.md line 163 states: 'Read-heavy commands (query, graph, orphans, context, the check/... cap their output...)' — but computeOrphans/renderReport emit every orphanTask/danglingLink with no total/shown/truncated fields and no cap, confirmed by test/orphans.test.ts:311 asserting all 700,000 rows appear verbatim in plain-mode stdout. A large Backlog snapshot or bundle would exhaust CI logs or an agent's context window exactly as ADR-0005 warns against.

#### `src/commands/replace.ts:125` — core/replace.ts's MANAGED_MARKERS registry protects only the index block, not the `<!-- lore:tasks:begin/end -->` block, so `lore replace` can silently corrupt machine-owned task rows despite the documented 'never touch managed regions' guarantee.

*Category: correctness · Cluster: `cmd-crud-a`*

Repro confirmed: replaceInText() run against text containing a well-formed lore:tasks managed block with a row title 'foo thing' replaces 'foo' inside that row (producing 'BAR thing'), i.e. matches inside the task block are neither skipped nor left uncounted. This directly contradicts docs/reference/cli-surface.md's explicit promise ('Skips lore-managed regions (managed task blocks, generated index listings)'). MANAGED_MARKERS in src/core/replace.ts still lists only the index markers; the LORE-22 task-block engine (managed-block.ts, shipped after replace.ts) was never wired into this registry.

#### `src/commands/schema.ts:156` — A full export's pruneOrphans deletes every `*.schema.json` in the resolved `--out` directory that the current profile doesn't emit, with no restriction to a lore-owned directory — `--out .` or any shared/non-default directory has all matching files silently, irreversibly rmSync'd.

*Category: correctness · Cluster: `cmd-meta-a`*

Running `lore schema export --out .` (or any directory that happens to hold unrelated `foo.schema.json` files, e.g. a shared schemas folder) deletes those unrelated files with no confirmation and no way to recover them — verified by reading `pruneOrphans` (schema.ts:146-167), which only filters by filename suffix, not by directory ownership, and by the test suite (test/schema-export.test.ts) which only exercises pruning against the default `.lore/schemas/` directory.

#### `src/commands/scaffold.ts:113` — Scaffold writes follow symlinks, so a symlinked docs/website ancestor or a symlinked final target file can redirect generated (or --force-overwritten) content outside the repo root.

*Category: security · Cluster: `cmd-meta-c`*

The preflight at scaffold.ts:113-114 uses statSync (follows symlinks) not lstatSync. More importantly, the actual writes in fswrite.ts's writeAllOrRollback use plain mkdirSync/writeFileSync (createIfAbsent's `wx` guards regular-vs-nonregular but still follows symlinked ancestor directories; writeFileOverwriting under --force follows a symlink at the final path and writes through to its target). If an attacker-controlled repo checkout contains e.g. `mkdocs.yml -> /home/user/.ssh/authorized_keys` or a symlinked `docs/` ancestor, running `lore scaffold mkdocs --force` writes generated content to that external target instead of refusing. This is the same symlink-escape class the codebase already defends against for reads (bundle.ts, replace.ts use lstatSync and explicitly skip symlinks) but the write paths (scaffold/agents) have no equivalent guard.

#### `src/commands/args.ts:68` — `assertNotReservedStem` (and the rest of the id-parsing pipeline through `runRename`) validates only the reserved basenames, never rejecting `..`-traversal segments in the destination id, so `lore rename` can move a concept's file to a path outside `docs/`.

*Category: security · Cluster: `cmd-meta-d`*

`lore rename docs/foo '../../tmp/escaped'` — `idFromPath` normalizes but does not strip `..`, `rewriteInbound`'s `toPath` becomes `../../tmp/escaped.md`, and `commands/rename.ts`'s `join(docsRoot, plan.rename.to)` resolves outside the repo (reproduced directly: `join('/repo/docs','../../tmp/escaped.md')` → `/tmp/escaped.md`). The absolute-path variant of the claim does not hold (`node:path.join` neutralizes a leading `/` in the second argument, so `/etc/passwd` as a destination stays inside `docsRoot`), but the `..`-segment escape is real and unguarded anywhere in the pipeline (`rename.ts`, `rewrite.ts`, `args.ts`).

#### `src/commands/init.ts:61` — `lore init` follows a pre-existing symlink occupying a scaffold directory (`.lore`, `.lore/schemas`, `docs`), so `ensureDir`'s recursive `mkdirSync` and `createIfAbsent`'s `wx` write both traverse the symlink and create files outside the repo root.

*Category: security · Cluster: `cmd-meta-d`*

A cloned repo (or a prior malicious step) has `docs` (or `.lore`) already replaced by a symlink to an external directory (e.g. `/tmp/evil` or a sensitive path). Running `lore init` creates scaffold files (`docs/index.md`, `.lore/config.toml`, etc.) inside that external target, not inside the repo — verified by reproduction: `mkdirSync(join(cwd,'docs'),{recursive:true})` + `writeFileSync(join(cwd,'docs','index.md'),...,{flag:'wx'})` against a pre-existing `docs -> /outside` symlink actually wrote `/outside/index.md`.

#### `src/commands/rename.ts:122` — The destination id (`newId`) is never confined to the bundle root — an id like `../outside` or an absolute path normalizes via `idFromPath`/`posix.normalize` into `toPath`, and `join(docsRoot, plan.rename.to)` in `assertTargetFree`/`commitWrites` then resolves outside `docs/`, so `lore rename` can write/move a file anywhere on disk.

*Category: security · Cluster: `cmd-rename-supersede`*

`lore rename reference/orders ../../../../tmp/pwned` (or any id whose segments net-negative through `..`) makes `assertTargetFree` check a path outside `docsRoot`, then `commitWrites`/`moveFile` writes and relocates the renamed concept's content to that outside path — a real containment escape, unlike the identical hazard in `commands/new.ts`'s `resolveOutPath`, which explicitly guards against `..`/absolute escape for exactly this class of operation (`--out`).

#### `src/commands/rename.ts:131` — `assertNotReservedStem` is called only on `newId`, not on `oldId` — unlike `supersede.ts` which checks both — so renaming FROM the reserved root `index` concept (docs/index.md, which does carry frontmatter and loads as a real graph concept, per the codebase's own established distinction between the frontmatter-free child indexes and the concept-valued root index) is not rejected up front.

*Category: correctness · Cluster: `cmd-rename-supersede`*

`lore rename index notes/moved`: `mergeIndexWrites` regenerates docs/index.md's managed listing against the post-rename graph (index.md's original disk bytes spliced with a fresh, now-self-excluding listing) and `commitWrites` writes that regenerated content into the source path, then immediately overwrites it again with the moved concept's own rewritten bytes, then renames the source away — so after the command, `docs/index.md` (the bundle's mandatory root hub) no longer exists on disk at all; its content is stranded at the new id and the root index is gone. This is not reachable for `log.md` (which stays frontmatter-free and is never a loadable concept), but it is reachable for `index` at the bundle root.

#### `src/core/bundle.ts:275` — An unreadable nested bundle directory is silently skipped during the walk, producing an incomplete graph that mutation commands (rename/supersede) still commit against.

*Category: correctness · Cluster: `core-bundle-check`*

docs/some-dir loses read permission (e.g. a CI checkout quirk, restrictive umask, or a partially-mounted volume). `lore rename old new` calls loadBundle, which skips the unreadable dir with only an advisory warning (walkFiles catch at line ~281). `rewriteInbound` then only sees the concepts that WERE loaded, so any inbound link from a concept inside the unreadable directory to the renamed concept is never rewritten. `commitWrites` (rename.ts:161) runs unconditionally regardless of the warning — verified rename.ts flushes advisories only after committing, never gates on them — so the rename reports success while leaving stale/broken links in the skipped directory.

#### `src/core/bundle.ts:158` — loadBundle never accepts or forwards a Profile, so every graph-backed command validates concept frontmatter against the built-in default profile even when a project has a custom .lore/profile.toml.

*Category: correctness · Cluster: `core-bundle-check`*

A project defines a custom .lore/profile.toml (custom types/fields/enums). validateFrontmatter defaults to defaultProfile() whenever options.profile is undefined (concept.ts), and LoadBundleOptions has no profile field, so tryParseConcept is always called without one from loadBundle. Every command that calls loadBundle (query, context, graph, orphans, rename, tasks, sync, link, supersede) then throws a validation error on a concept that is perfectly valid under the project's own profile, or fails to catch a concept that violates it. sync.ts and supersede.ts even call loadProfile() separately but only use it for later serialization, never for the loadBundle call itself, confirming this isn't a caller-supplies-it-elsewhere false alarm.

#### `src/core/profile.ts:442` — Field/item/type declarations in profile.toml silently ignore unknown attribute keys (no allowlist enforcement), so a typo like `require = true` (vs `required`) or `sectons = [...]` silently weakens validation with no warning or error.

*Category: correctness · Cluster: `core-bundle-check`*

A profile author writes `[types.fields.owner]` with `require = true` (typo for `required`). `parseFieldSpec` only reads `table.required`/`table.enum`/`table.kind`/`table.items`/`table.default` by name; the misspelled `require` key is never read or flagged, so `required` silently defaults to `false` and every concept validates clean even when missing that field entirely. Verified: parseTypes/parseFieldSpec/parseItems have no unknown-key check anywhere, and the codebase's own parseProfile docstring (line 309) explicitly scopes the documented 'unknown key is ignored, forward-compatible' contract to only the top-level/`[profile]` table — nested field/type/item tables are not covered by that stated design, so the silent tolerance there is an unintended gap rather than the documented policy.

#### `src/core/concept.ts:262` — yaml.load has no alias/anchor limits and YAML_DUMP_OPTIONS sets noRefs:true, so a small frontmatter payload using nested YAML anchors expands exponentially on serialize, causing memory exhaustion / an uncaught RangeError instead of a clean LoreError.

*Category: security · Cluster: `core-concept-manifest`*

Repro'd directly: an 18-level doubling-anchor chain (~417 bytes of YAML: `a0: &a0 [x,x]` then `a{i}: &a{i} [*a{i-1},*a{i-1}]` repeated) parses instantly (aliases stay shared references) but yaml.dump(..., {noRefs:true}) — exactly YAML_DUMP_OPTIONS — expands it to a 64MB string in ~600ms; a few more levels reaches GB/OOM territory or a V8 'Invalid string length' RangeError. serializeConcept is reached broadly (bundle.ts's estimateTokens, sync.ts, rewrite.ts, indexes.ts, template.ts, scaffold.ts, commands/link.ts, commands/supersede.ts), so a single crafted concept file anywhere in the bundle can DoS most lore commands the next time they touch it, and the crash is an unhandled RangeError, not the module's own LoreError contract.

#### `src/core/indexes.ts:285` — locateManagedBlock's first-begin/last-end recovery silently deletes authored prose between duplicate marker blocks (or after an unmatched begin) instead of failing loudly.

*Category: error-handling · Cluster: `core-index-context`*

A merge conflict (or hand edit) leaves an index.md with two well-formed <!-- lore:index:begin/end --> blocks and hand-written prose ('mid') between them; the next `lore sync` collapses everything from the first begin to the last end into the regenerated block, permanently deleting 'mid' with no warning. test/indexes.test.ts:134-144 explicitly asserts this collapse ('no stale region survives'). A truncated block (begin with no end) is likewise rewritten to EOF, discarding anything after the orphan begin.

#### `src/core/replace.ts:84` — The MANAGED_MARKERS registry only protects `<!-- lore:index:begin/end -->` blocks; it was never updated with the `<!-- lore:tasks:begin/end -->` markers that managed-block.ts (LORE-22, shipped 2026-07-02, four days after replace.ts landed on 2026-06-28) added, so `lore replace` edits and counts matches inside a Story/Spec's live task table.

*Category: correctness · Cluster: `core-replace`*

Reproduced directly: replaceInText() on a doc containing a `<!-- lore:tasks:begin -->…<!-- lore:tasks:end -->` table with a `LORE-42` link, replacing "LORE-42"→"LORE-99", rewrote the id inside the managed table (and reported count:2, matching both the table cell and the prose occurrence) instead of skipping the machine-owned block. The file's own docstring (lines 26-34) explicitly documents that a match overlapping a managed region must be "left untouched and uncounted" and calls out `<!-- lore:tasks -->` as a marker the registry was meant to cover — that promise was never fulfilled after LORE-22 shipped. The next `lore sync` will regenerate the task block from live Backlog data and silently clobber the replace-corrupted table (or, if sync's regeneration happens to reproduce different bytes, leave a table whose id no longer matches its own link target).

#### `src/core/rewrite.ts:164` — rewriteInbound/idFromPath never confines fromId/toId to the docs/ bundle root, and no command-layer validation catches a traversal id either — unlike the sibling `lore new --out` path, which explicitly confines a caller-supplied path to the bundle root via resolveOutPath's `..`-segment/isAbsolute checks.

*Category: security · Cluster: `core-rewrite-engine`*

`lore rename docs/reference/orders ../../outside` (or a typo'd relative id) produces a RewritePlan with `rename.to = "../../outside.md"`; rename.ts's commitWrites does `join(docsRoot, plan.rename.to)` and `moveFile`, relocating/overwriting a file outside docs/ — verified by reading idFromPath (core/concept.ts) and rename.ts's commitWrites/assertTargetFree, which apply no containment check analogous to new.ts's resolveOutPath.

#### `src/core/rewrite.ts:434` — destRangeForDefinition locates a reference definition's closing label bracket with `body.indexOf("]", span.start)`, which is not escape-aware, so a label containing an escaped `]` (e.g. `[a\]x:y]: ../reference/orders.md`) matches the escaped bracket instead of the real one and mis-locates the destination range.

*Category: correctness · Cluster: `core-rewrite-engine`*

Reproduced directly: `writeDoc("stories/bulk.md", "...See [ref][a\\]x:y] for more.\n\n[a\\]x:y]: ../reference/orders.md\n")` then `rewriteInbound(graph, "reference/orders", "reference/sales-orders", {move:true})` rewrites the definition line to `[a\]x:../reference/sales-orders.md ../reference/orders.md` — the label is corrupted and the old destination is left dangling in the body, exactly as Codex described.

## Medium-severity findings

Grouped by review cluster. Each is a real, adjudication-confirmed issue — see the cluster
key to locate the exact files reviewed together.

**adapter-backlog**
- `src/adapters/backlog.ts:684` (security) — Task IDs, labels, titles, and queries are pushed as argv values with no option-termination (--) or leading-dash validation before hitting Backlog's own flag parser
- `src/adapters/backlog.ts:774` (correctness) — createTask can succeed at the Backlog layer (task actually created) yet still throw a drift error if the `Created task <ID>` line fails to parse, discarding the new id

**build-ci-config**
- `.github/actions/setup-bun/action.yml:11` (security) — External actions (oven-sh/setup-bun@v2, actions/checkout@v6, actions/cache@v5, actions/upload-artifact@v4, actions/setup-python@v6, actions/setup-node@v5) are pinned to mutable major-version tags rather than full commit SHAs.
- `.github/workflows/release.yml:101` (test-coverage) — verify-versions only checks version/license/author/repository/optionalDependencies-pin consistency across the six packages; it never checks each platform package's `os`/`cpu`/binary filename, and only linux-x64 is actually executed (the other four platforms just get a size check).
- `docker/e2e/docker-compose.yml:3` (test-coverage) — The ~1500-line Docker e2e harness (run-e2e.sh) is documented only as a manual `docker compose` command and is not invoked by either CI workflow, so it provides no merge/release gate.
- `package.json:2` (correctness) — All six scoped packages lack `publishConfig.access: public` (or an equivalent `--access public` in the not-yet-written publish job), which npm requires for a scoped package's first publish.

**build-runtime**
- `docker/e2e/Dockerfile:11` (security) — Base image pinned only by tag (not digest), NodeSource setup script is piped into a root shell, and mkdocs packages are installed as floating version ranges.
- `docker/e2e/docker-compose.yml:13` (error-handling) — Host bind mount for /results plus the image's fixed non-root UID 1000 can hit host permission mismatches on Linux, and report-write failures inside run-e2e.sh are not surfaced.
- `docker/e2e/docker-compose.yml:4` (error-handling) — The documented `docker compose -f docker/e2e/docker-compose.yml up --build` command does not itself propagate the e2e service's exit code to the caller's shell/CI job.
- `docker/e2e/run-e2e.sh:34` (correctness) — record() uses `jq -n` (pretty multi-line output) for a file named/documented as report.jsonl, so the committed report is not actually JSON Lines.
- `test/support/record-backlog-goldens.ts:14` (test-coverage) — The golden recorder reads a live, mutable task (default LORE-33) from this repo's own backlog/ and accepts any upstream CLI path via env var with no version/commit provenance check.

**cli-entry-state**
- `src/cli.ts:111` (api-design) — `--help`/`-h` is recognized anywhere before a `--`, including after the command token, so `lore query --help` renders the generic top-level command catalog instead of query's own detailed help.
- `src/config.ts:146` (error-handling) — readConfigText's catch-all maps every non-ENOENT read failure (including EACCES/EPERM permission errors) to a `validation` LoreError, contradicting the codebase-wide EACCES/EPERM → `denied` contract used everywhere else.
- `src/state.ts:210` (error-handling) — commitBacklogFiles captures only LoreError.message into BacklogCommitResult.error on a git commit/add failure, discarding the LoreError.hint that carries the actual git/hook stderr reason.

**cmd-check**
- `src/commands/check.ts:709` (performance) — probeLiveness's unique-URL worklist has no maximum size or total wall-clock deadline; only per-URL concurrency (8) and per-request timeout (5s) are bounded.
- `src/commands/check.ts:358` (concurrency) — resolveSharedReconciliation's call into resolveTaskDetails fans out `adapter.viewTask(id)` for every distinct linked task id fully concurrently (Promise.allSettled over the whole array), with no bounded worker pool, unlike the liveness prober's explicit mapWithConcurrency(8).
- `src/commands/check.ts:157` (error-handling) — When reconciliation's DriftResult carries a real error, runCheck still `emit()`s the check.report (with whatever findings were collected before the failure) and only rethrows afterward — the emitted report has no `complete: false`/operational-failure marker distinguishing it from a genuinely clean run.
- `src/commands/check.ts:463` (correctness) — `docPath` is built by naively concatenating the raw, unnormalized `bundle.label` (the CLI-supplied root string) with the concept's path, whereas `isDocsRoot` (line 504-506) explicitly normalizes backslashes/trailing slashes/case before comparing — the two treatments of the same `label` are inconsistent.
