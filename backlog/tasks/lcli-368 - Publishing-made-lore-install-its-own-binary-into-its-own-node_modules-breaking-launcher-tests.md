## Description

<!-- SECTION:DESCRIPTION:BEGIN -->
Publishing 0.3.5 broke CI for every subsequent PR, in two chained ways, and both were latent from the release commit rather than caused by any later change.

FAILURE 1 — STALE LOCKFILE. The release commit bumped package.json and all six npm/<platform>/package.json files to 0.3.5, including the root's exact optionalDependencies pins, and did NOT regenerate bun.lock. bun.lock still resolved @opum-ai/lore-<platform> at 0.3.4. Every CI job died at 'error: lockfile had changes, but lockfile is frozen' in setup-bun, BEFORE any gate ran — all eight checks red with a single cause.

Why it did not fail immediately: at the time of the bump the 0.3.5 packages did not exist on the registry, so nothing could resolve them and the drift was invisible. PUBLISHING MADE THE LATENT MISTAKE RESOLVABLE, AND THEREFORE VISIBLE. Regenerated with bun 1.3.14 specifically — the pinned version. quest-cli hit the identical failure on their own bump and warned that regenerating with a different Bun writes a different lockfile shape and fails the frozen check a second time for a new reason; my local Bun is 1.2.23, so I fetched 1.3.14 rather than use it.

FAILURE 2 — THE MORE INTERESTING ONE. lore lists its own platform packages as optionalDependencies AT THE VERSION UNDER DEVELOPMENT. Once 0.3.5 existed on the registry, 'bun install' placed lore's own compiled binary at <repo>/node_modules/@opum-ai/lore-darwin-arm64. That broke all six bin/lore.cjs launcher tests.

The mechanism is worth understanding rather than just patching: those tests point NODE_PATH at a fixture directory holding a stub platform package. But NODE_PATH is only a FALLBACK — Node first walks UP from the script's own location looking for node_modules, and the repository is an ancestor of bin/lore.cjs. So the real installed package now wins the ancestor walk and shadows the fixture. THE TESTS WERE PASSING BY ACCIDENT: they depended on the real package being absent, which was true only until the version under development was published.

Fixed by running a COPY of the launcher from inside the fixture directory, so the fixture's node_modules is on the ancestor path and resolution finds the stub for the same reason a real install finds the real package. Proven by negative control: reverting to the repository's own launcher makes all six fail again; restored, all six pass.

WHAT MAKES THIS RECURRING RATHER THAN ONE-OFF: it will happen again at every release. The moment 0.3.6 publishes, a dev tree on 0.3.6 installs its own 0.3.6 binary. The launcher-test fix is version-independent, so it holds — but anything else that assumes 'lore's own platform package is not installed here' has the same latent dependency on a version not yet existing.
