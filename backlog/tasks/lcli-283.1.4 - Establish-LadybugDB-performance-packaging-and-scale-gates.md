## Description

<!-- SECTION:DESCRIPTION:BEGIN -->
Prove that the persistent index improves repeated retrieval at acceptable startup, memory, disk, packaging, and concurrency cost across Lore supported platforms before M6 is accepted.
<!-- SECTION:DESCRIPTION:END -->

## Acceptance Criteria
<!-- AC:BEGIN -->
- [ ] #1 Benchmarks report cold build, warm open, graph, query, and context latency plus memory and disk usage on versioned small and large fixtures
- [ ] #2 M6 defines quantitative regression thresholds and demonstrates a material warm-query improvement without unacceptable small-repository regression
- [ ] #3 Node and Bun distribution paths pass supported native platform install, build, smoke, and clean-uninstall tests
- [ ] #4 Single-writer and multi-reader scenarios, CLI and future long-running-process contention, crash recovery, and file-lock diagnostics are tested
<!-- AC:END -->

## Implementation Plan

<!-- SECTION:PLAN:BEGIN -->
1. Freeze benchmark fixture schema `ladybug-benchmark-fixture/1` under `benchmark/ladybug/fixtures/v1/` and add a deterministic seeded generator plus digest tests. `small.json` will generate exactly 64 concepts, 128 tasks, 512 authored edges, and 1 MiB of Markdown body bytes; `large.json` will generate 4,096 concepts, 4,096 tasks, 32,768 authored edges, and 64 MiB of body bytes. Both fixtures will cover chains, stars, cycles, duplicate and dangling edges, Unicode, additive fields, common/rare/tied/no-hit lexical queries, graph depths, and context budgets. The committed specs will include expected canonical export, source-inventory, and task-snapshot SHA-256 values; generated repositories and caches stay temporary and untracked. (AC #1)
2. Add a benchmark-only worker and orchestrator under `benchmark/ladybug/` without a public backend flag or lifecycle change. A fresh worker process will select the existing injected `indexed` or `reference` policy, verify identical result digests first, and then measure: projection-cold build with no generation; fresh-process warm generation validation/open/reconstruction with an existing immutable generation; warm graph, query, and context operations; `Bun.spawn` wall and CPU time; subprocess `resourceUsage().maxRSS` bytes; canonical input bytes; emitted bytes; and recursive logical bytes only below `.lore/cache/graph/ladybug/1`. Cold means projection-cold, not an unverifiable OS page-cache flush. Every run will hash docs, Backlog, profile, Git metadata, and non-cache `.lore` bytes before and after so any source write fails the run. (AC #1)
3. Emit one ordered `lore.ladybug-benchmark/1` JSON document containing exact Lore, Bun, Node, Ladybug package/runtime/storage, OS/arch, runner image, CPU/RAM, commit/dirty state, fixture version/digests/counts, seed, scenario definitions, warmups, repetitions, randomized AB/BA order, every raw sample, median, p95, MAD, paired ratios, one-sided 95% bootstrap intervals, resource totals, gate definitions, and pass/fail/inconclusive reasons. Cold build uses 1 discarded setup plus 7 fresh generated-repository repetitions; warm open and each command use 5 discarded warmups plus 30 measured repetitions in three interleaved batches. A calibration workload with coefficient of variation above 10% makes timing evidence `inconclusive` and requires a rerun; it never silently passes. Schema/golden/digest tests will make the report machine reproducible while host facts and raw measurements remain honest evidence rather than byte-identical fiction. (AC #1, #2)
4. Freeze thresholds before collecting the acceptance run: cold-build p95 at most 2 s small / 30 s large; warm-generation-open p95 at most 350 ms small / 3 s large; cold peak RSS at most 512 MiB small / 2 GiB large; warm command peak RSS at most 384 MiB small / 1 GiB large; index logical bytes at most 64 MiB small and, for large, both 512 MiB and `64 MiB + 4 * canonicalExportBytes`. The primary material-improvement gate is large warm query indexed/reference median ratio at most 0.60, p95 ratio at most 0.75, and upper one-sided 95% interval for the paired median ratio at most 0.75. Large graph/context may not regress beyond 1.10 median or 1.20 p95. For every small warm open/graph/query/context case, indexed median regression is capped at the larger of 15 ms or 15%, and p95 regression at the larger of 30 ms or 25%. These are product budgets, not values fitted to the first result; changing them requires a reviewed task-plan update with the failed evidence retained. (AC #2; approval required)
5. Keep pull-request CI non-timing-gated: fixture determinism, JSON schema, result parity, resource accounting, and one-repetition benchmark smoke run there. Add a fixed `ubuntu-24.04` x64 release-qualification job that runs the full paired methodology with no services or parallel benchmark jobs, uploads the JSON evidence, and gates the existing release package/publish chain only on conclusive threshold success. Relative paired gates, robust statistics, three interleaved batches, generous independent resource ceilings, and explicit `inconclusive` reruns prevent noisy shared-runner timing from becoming either a flaky failure or a false pass. Darwin-arm64 local results from pinned Bun 1.2.23 will be recorded separately as supplemental evidence; matching-host CI, not cross-compilation or local Darwin results, is required for Linux and Windows claims. (AC #1, #2)
6. Extend the existing five-package release matrix with matching-host qualification: `macos-latest` (Darwin arm64), `macos-15-intel` (Darwin x64), `ubuntu-24.04-arm` (Linux arm64), `ubuntu-24.04` (Linux x64), and `windows-latest` (Windows x64). On each host, run an isolated frozen install; assert the exact `@ladybugdb/core@0.18.2` optional package, OS/CPU metadata, integrity, and copied `lbugjs.node`; compile the matching Bun target on the same host; pack the root launcher and matching Lore platform package; install both tarballs into a new Node project; run Node-launcher version/help plus graph/query/context; move the Bun executable away from the checkout and repeat the smoke; uninstall root and platform packages; and assert the launcher, package directories, addon, install scratch, and global locations are clean. Uninstall will not delete repository-local user cache implicitly; explicit contained cache disposal and source preservation are tested separately. Preserve the six-package publication order and all five Lore distribution packages. (AC #3; uninstall policy approval required)
7. Qualify native indexing only where executable evidence passes. The initial candidate native-index set is Darwin arm64/x64 and Linux arm64/x64. For Windows x64, a sacrificial child process will probe the exact addon and record its exit/signal; the main test process must still prove import-safe CLI, install, compile, launcher, graph/query/context reference fallback, no database creation, clean uninstall, and stable output under the known Bun 1.2.23 addon segfault. The five-platform distribution contract remains unchanged, but Windows native-index support is not claimed. If approval instead requires native indexing on all five distribution targets, leave AC #3 and LCLI-283.1.4 open until Bun/Ladybug supplies executable Windows evidence; never convert package availability or cross-compilation into a support claim. (AC #3; platform decision approval required)
8. Add `test/ladybug-concurrency.test.ts` plus a test-only subprocess helper. Cover at least eight simultaneous read-only processes against one immutable generation; multiple connections in one long-running read-only process; an old-generation reader held open while one writer builds and atomically publishes a new generation; two missing-generation writers racing with exactly one owner and safe reuse/fallback; reusable and stale-source behavior under a live Lore writer lock; native same-file read-only/read-write conflict classification; stable redacted lock/dispose diagnostics; and unchanged deterministic result digests. Kill real child writers after database close, after control-manifest fsync, after atomic rename, and before lock release, then prove staging cleanup, stale-lock recovery, immutable-generation reuse/rebuild, no partial output, cache containment, and byte-identical repository sources. Keep public Cypher, native IDs, addon failures, and lock-owner secrets out of outputs. (AC #4)
9. Map executable evidence directly to the task: AC #1 gets fixture digest tests plus the full JSON report; AC #2 gets the committed gate file and conclusive Linux-x64 qualification artifact plus separate Darwin-local report; AC #3 gets five matching-host install/build/pack/Node-launcher/Bun-binary/uninstall job logs and artifact manifests, with four native-index verdicts and an explicit Windows fallback verdict; AC #4 gets focused multi-process contention/crash tests and their source/cache hash inventory. Required commands include `bun benchmark/ladybug/run.ts --fixture small --fixture large --output artifacts/ladybug-benchmark-v1.json`, focused benchmark/concurrency/lifecycle/indexed/release tests, and matching-host release workflow jobs. No acceptance box is checked from cross-compile-only, skipped, simulated-platform, or package-metadata evidence.
10. After implementation only, run exact Bun 1.2.23 frozen install, package dry-run, audit, all focused tests, full `bun test --isolate`, lint, typecheck, source and compiled builds/smokes, the five matching-host qualification matrix, the conclusive benchmark gate, `lore sync`, `lore validate --strict`, `lore check --strict`, `git diff --check`, and tracked/untracked/cache/source-write audits. Update architecture, tech stack, release publishing, roadmap, and campaign handover only outside Lore-managed regions; record raw evidence and any approved platform limitation; then follow task-finalization without advancing parent LCLI-283.1 until every child gate is genuinely complete. Implementation remains blocked on explicit approval of the thresholds, fixture scale, Windows fallback-only native policy, uninstall/cache policy, and release-gate placement above.
