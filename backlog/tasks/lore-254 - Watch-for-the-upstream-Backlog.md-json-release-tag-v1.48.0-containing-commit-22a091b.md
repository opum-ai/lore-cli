## Description

<!-- SECTION:DESCRIPTION:BEGIN -->
## Outcome
A reliable signal that fires when MrLesk/Backlog.md publishes a tag NEWER than v1.48.0 whose history includes commit 22a091b (PR #790 / BACK-545), so the adapter-migration work (LORE-253) can be picked up promptly instead of sitting stale.

## Why it matters
lore's entire first-release gate hinges on this one upstream event, and nothing currently watches for it. The latest upstream tag (v1.48.0, 2026-07-12) is 10 commits behind the --json merge. Without a trigger, LORE-253 and lore's first release can stall indefinitely after upstream ships.

## Context
Companion to LORE-253 (the migration this unblocks). A lightweight approach: a scheduled CI check or a documented cadence that queries the MrLesk/Backlog.md releases API and asserts the tag's commit is at/past 22a091b — or probes the released binary for --json directly.
<!-- SECTION:DESCRIPTION:END -->

## Acceptance Criteria
<!-- AC:BEGIN -->
- [ ] #1 A mechanism (scheduled CI job, release-watch, or a documented manual cadence) detects a new MrLesk/Backlog.md tag whose history contains commit 22a091b and surfaces it to the maintainer.
- [ ] #2 It distinguishes a --json-capable tag from a plain one (asserts the commit is an ancestor of the tag, or probes the released binary for --json), not just any new tag.
- [ ] #3 Where the signal lands and who acts on it is documented, linking to the migration task (LORE-253).
<!-- AC:END -->

## Implementation Plan

<!-- SECTION:PLAN:BEGIN -->
1. Decision (recorded here + in notes): detect via GitHub compare API ancestor-check
   (base=22a091b...head=<tag sha>, status in {identical,ahead}) against MrLesk/Backlog.md's
   Releases API -- not a released-binary --json probe -- because it's cheaper (no per-platform
   binary download/exec on the runner), matches the task's own first-listed Context option, and
   is exactly what AC#2 names as sufficient ("asserts the commit is an ancestor of the tag").
2. Add src/scripts/upstream-backlog-watch.ts: a standalone maintenance script (NOT a `lore`
   command -- no --json envelope/exit-code contract) with pure, unit-testable helpers
   (candidateReleases date-cutoff prefilter, isAncestorCompareStatus, renderIssueBody) plus a
   dependency-injected I/O layer (Fetcher param) so `watchOnce()` is testable against a stub
   fetch with no network. Logic: skip entirely if a GitHub issue labeled `upstream-watch`
   already exists in THIS repo (open OR closed -- stateless one-time-ever surfacing, since once
   found every later upstream release also contains the commit forever); else scan
   MrLesk/Backlog.md releases newest-first, bounded to releases published at/after the PR #790
   merge date (2026-07-16), ancestor-check each candidate's tag commit against 22a091b, and on
   the first hit open a labeled tracking issue in this repo linking LORE-253.
3. Add .github/workflows/upstream-backlog-watch.yml: scheduled (daily cron) + workflow_dispatch,
   checkout + setup-bun + `bun run src/scripts/upstream-backlog-watch.ts` with
   GITHUB_TOKEN=github.token, permissions {contents: read} at workflow level and
   {issues: write} on the job (least privilege, matches ci.yml's style).
4. Add test/upstream-backlog-watch.test.ts: unit tests for the three pure helpers plus
   watchOnce() integration tests against a stub Fetcher covering (a) already-surfaced skip,
   (b) no qualifying release yet, (c) a qualifying release triggers label-ensure + issue-create
   with LORE-253 mentioned in the body, (d) a newer-but-non-ancestor tag is correctly NOT
   treated as a match (AC#2's core assertion).
5. Add docs/runbooks/upstream-backlog-watch.md via `lore new runbook` documenting: what the
   workflow does, exactly where the signal lands (a GitHub issue labeled `upstream-watch` in
   this repo) and who acts on it (the maintainer, starting LORE-253), plus links to
   backlog-json-patch.md §8.1 and release-publishing.md's Prerequisites. Add its entry to
   docs/index.md's hand-authored Runbooks bullet list (runbooks/index.md's own list is a
   lore-managed block, regenerated by `lore sync`).
6. bun test / bun run typecheck / bun run lint / bun run src/cli.ts check must all be green;
   commit backlog/ status edits alongside the code in Conventional Commits with Refs: LORE-254.
