## Description

<!-- SECTION:DESCRIPTION:BEGIN -->
Publishing 0.3.5 broke CI for every subsequent PR, in two chained ways, both latent from the release commit rather than caused by any later change.

FAILURE 1 — STALE LOCKFILE. The release commit bumped package.json and all six npm/<platform>/package.json files to 0.3.5, including the root's exact optionalDependencies pins, and did NOT regenerate bun.lock, which still resolved the platform packages at 0.3.4. Every CI job died at 'lockfile had changes, but lockfile is frozen' in setup-bun BEFORE any gate ran — all eight checks red with a single cause.

Why it did not fail immediately: at the time of the bump the 0.3.5 packages did not exist on the registry, so nothing could resolve them and the drift was invisible. PUBLISHING MADE THE LATENT MISTAKE RESOLVABLE, AND THEREFORE VISIBLE. Regenerated with bun 1.3.14 — the PINNED version. quest-cli hit the identical failure on their own bump and warned that regenerating with a different Bun writes a different lockfile shape and fails the frozen check a second time for a new reason; my local Bun is 1.2.23, so I fetched 1.3.14 rather than use it.

FAILURE 2 — THE MORE INTERESTING ONE. lore lists its own platform packages as optionalDependencies AT THE VERSION UNDER DEVELOPMENT. Once 0.3.5 existed, 'bun install' placed lore's own compiled binary at <repo>/node_modules/@opum-ai/lore-darwin-arm64, breaking all six bin/lore.cjs launcher tests.

The mechanism is worth understanding rather than just patching. Those tests point NODE_PATH at a fixture directory holding a stub platform package. But NODE_PATH is only a FALLBACK — Node first walks UP from the script's own location looking for node_modules, and the repository is an ancestor of bin/lore.cjs. So the real installed package wins the ancestor walk and shadows the fixture. THE TESTS WERE PASSING BY ACCIDENT: they depended on the real package being absent, which was true only until the version under development was published.

Fixed by running a COPY of the launcher from inside the fixture directory, so the fixture's node_modules is on the ancestor path and resolution finds the stub for the same reason a real install finds the real package. Version-independent, so it holds at 0.3.6 and after. Proven by negative control: reverting to the repository's own launcher makes all six fail again; restored, all six pass.

WHAT MAKES THIS RECURRING RATHER THAN ONE-OFF: it happens at every release. The moment 0.3.6 publishes, a dev tree on 0.3.6 installs its own 0.3.6 binary.

AC#4 SWEEP RESULT, 2026-08-30 — the assumption exists nowhere else.

RESOLUTION SHADOWING IS CONFINED TO ONE FILE. 'grep -rln NODE_PATH test/ src/ benchmark/' returns exactly test/bin-lore.test.ts. Nothing else depends on Node's module-resolution order, so nothing else can be shadowed by lore's own platform package appearing in node_modules.

THE OTHER FILES THAT NAME THE PLATFORM PACKAGES DO NOT ASSUME ABSENCE. test/ladybug-qualification-evidence.test.ts, test/ladybug-package-qualification.test.ts, benchmark/ladybug/qualification-evidence.ts and benchmark/ladybug/package-qualification.ts build and install into throwaway prefixes they create, so they control their own tree rather than inheriting the repository's. scripts/publish-release.sh addresses tarballs by explicit path.

EMPIRICAL HALF, which matters more than the reading: the full suite passes 2772/0/1 on the PINNED bun 1.3.14 with lore's own @opum-ai/lore-darwin-arm64@0.3.5 actually present in node_modules. That is the condition that broke the six launcher tests, and every other test runs green under it.

Both halves were needed. The grep says nothing else uses the mechanism; the run says nothing else breaks under the condition. Either alone would have been weaker — a grep cannot see an implicit dependency, and a green run on its own does not tell you WHY it is green.
