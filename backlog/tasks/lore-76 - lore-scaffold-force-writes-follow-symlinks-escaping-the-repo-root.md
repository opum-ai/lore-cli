## Description

<!-- SECTION:DESCRIPTION:BEGIN -->
The scaffold preflight uses statSync (follows symlinks) rather than lstatSync, and the actual write path (fswrite.ts writeAllOrRollback) follows a symlinked ancestor directory or a symlinked final target under --force, writing generated content outside the repo. This is the same symlink-escape class the codebase already guards against on the read path (bundle.ts, replace.ts use lstatSync and skip symlinks) but the write paths have no equivalent guard.
<!-- SECTION:DESCRIPTION:END -->

## Acceptance Criteria
<!-- AC:BEGIN -->
- [x] #1 Scaffold write operations detect a symlink at any ancestor of the target path or at the final target itself and refuse to write through it (lstatSync-based check, matching the read-path convention)
- [x] #2 A test covers a symlinked ancestor directory and a symlinked final target under --force, both refused
<!-- AC:END -->

## Implementation Notes

<!-- SECTION:NOTES:BEGIN -->
Root cause: two distinct symlink-following gaps in the write path, both in
src/commands/fswrite.ts's writeAllOrRollback (the shared primitive scaffold's
mkdocs/docusaurus/obsidian targets all use):
1. ensureDir's mkdirSync(abs, {recursive:true}) for each plan directory transparently
   follows a symlinked ancestor (standard POSIX path resolution -- no mkdir flag can
   disable this for intermediate path components).
2. Under --force, the overwrite branch's existsSync/readFileSync/writeFileSync all
   follow a symlink at the FINAL target too, writing straight through to whatever the
   symlink points at. (The non-forced branch's createIfAbsent already used lstatSync
   via existingIsRegularFile for the exact-final-file case only -- that half was
   already safe; the ancestor-directory case and the whole --force path were not.)

Fix: added assertNoSymlinkInPath(root, relPath) to fswrite.ts -- walks every path
segment from root down to (and including) the target, lstatSync per segment (never
follows), throws a conflict LoreError naming the exact symlinked segment the moment
one is found; a segment that doesn't exist yet is fine (nothing to guard against).
Called at the top of writeAllOrRollback's directory loop (covers a symlinked
ancestor OR a symlinked directory target) and at the top of its per-file map
callback, BEFORE the force/non-force branch split (covers a symlinked ancestor OR a
symlinked final file, for BOTH write disciplines). Mirrors the codebase's existing
read-path convention (core/bundle.ts, commands/replace.ts: explicit
lstatSync(...).isSymbolicLink(), never a stat-follows-symlinks helper) rather than
inventing a new pattern. Scoped deliberately to writeAllOrRollback specifically
(scaffold's own single call site) rather than the much more widely-shared ensureDir
export (used by init.ts/agents.ts/sync.ts/new.ts/schema.ts/rename.ts) -- extending
ensureDir itself would have silently widened this task's scope into command paths
with their own separate tasks (LORE-77, for init.ts) or no task coverage at all.

Live end-to-end verification against the real CLI (scratch repos, real symlinks):
- Pre-fix repro reproduced the task's own claim exactly: `docs -> outside-dir`
  symlink + `lore scaffold mkdocs` wrote generated content into the outside
  directory; a `mkdocs.yml -> outside-dir/mkdocs.yml` symlink + `lore scaffold
  mkdocs --force` overwrote the outside file's real content with generated bytes
  (confirmed via `git stash` on fswrite.ts: read the outside file's content before
  and after, watched it change from "SECRET..." to the generated config).
- Post-fix: both scenarios now exit 5 (conflict) with a message naming the exact
  symlinked path segment; the outside file/directory content is verified byte-
  identical before and after (untouched).
- Since writeAllOrRollback is the SHARED write primitive for all three scaffold
  targets (mkdocs/docusaurus/obsidian -- confirmed via this file's own docstring
  and grep), this fix protects all three without per-target duplicate tests,
  matching this test file's own established "shared primitive, tested once"
  convention.

3 new tests added to test/consumer-scaffold.test.ts (a symlinked docs/ ancestor
directory without --force; a symlinked mkdocs.yml final target under --force,
asserting the outside file's exact bytes are unchanged; a symlinked ancestor under
--force too, confirming the guard fires regardless of write discipline).
Confirmed via git stash (isolating just fswrite.ts, keeping the new tests) that all
3 genuinely fail pre-fix (no exception thrown at all -- the write silently
succeeded) and all 49 pre-existing tests in that file are unaffected either way.

Full bun test: 1605 pass/0 fail (up from 1602). bun run typecheck clean. bunx
biome check clean (one formatter-only fix applied).
